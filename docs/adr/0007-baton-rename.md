# 0007. Renamed to Baton; the bundle id, launcher ids and log subsystem keep the old name

Status: accepted

## Context

Until 1.0 the app was called Claude Profiles. 1.0 is called Baton to keep "Claude", Anthropic's trademark, out of the product's own name; Claude Desktop is named only to say what Baton works with. Everything a person sees or types changes: the app, `Baton.app`, the `baton` command, the Homebrew cask, the repository and the launchers folder in `~/Applications`. People who already use Claude Profiles must keep their windows, sign-ins, launchers in the Dock and sessions, and an upgrade must never leave their data half in one folder and half in another.

## Decision

- **Identifiers the system depends on keep the old name.** The bundle id stays `io.github.trukhinyuri.claudeprofiles`, launchers stay `io.github.trukhinyuri.claudeprofiles.launcher.<id>`, and the log subsystem stays the bundle id. The one-copy-at-a-time check finds a running copy by bundle id, so the old and the new app see each other during the upgrade and never sync at once. The UserDefaults domain, Launch Services and privacy (TCC) records, Dock items of launchers and the cask's `zap` paths follow the bundle id too. Renamed Mac apps keep theirs: Slack still ships `com.tinyspeck.slackmacgap`, and the App Store doesn't allow changing it. Everything that is Claude's keeps Claude's name: `~/.claude`, `~/Library/Application Support/Claude`, Claude Desktop's own bundle id in the engines, and launchers named `Claude <LABEL>.app`.
- **The data folder keeps its name.** A fresh install keeps its data in `~/Library/Application Support/Baton`; an install from before 1.0 keeps using `~/Library/Application Support/Claude Profiles` where it is, whether it is a folder or a link to one, and it is never renamed, linked or mentioned by `baton doctor`. Absolute paths into it live where Baton can't safely rewrite them: every profile window's `--user-data-dir` and the Claude Code binaries Claude Desktop keeps in a profile's data, session cards, Claude Code's project keys and the archive baselines. A rename would have to rewrite all of them while no window runs, and a miss would split someone's data between two folders. A data folder's name need not match the app's: Visual Studio Code keeps its data in `~/Library/Application Support/Code`. `Paths` uses the Baton folder if it exists, else the Claude Profiles one if it leads to a folder, else the Baton folder.
- **The launchers folder is renamed in place, once.** `~/Applications/Claude Profiles` becomes `~/Applications/Baton`, the name people see in Finder, with one `rename(2)` (`renamex_np(RENAME_EXCL)`) and no link at the old name. `LegacyMigration` does it at app start, before any path is resolved, from `baton migrate`, and from `scripts/install-app.sh`, which runs the installed `baton migrate` when it installs into the old folder; never in demo mode. It takes an exclusive `flock` on `.baton-migration.lock` inside the data folder, which never moves; `baton open`, `add`, `refresh`, `continue`/`pass` and `remove` hold it shared while they run. Under the lock it reads the process list again right before the rename and keeps the old name while any process other than itself and its ancestors runs from inside the folder (an engine, its helpers, a launcher's script, a Baton), while a Claude window uses a profile's data, while another Baton app or CLI runs, while the app itself runs from inside the folder, and when the rename fails; a rename across volumes is never turned into a copy. Then it retries at the next start, and `baton doctor` and the status panel say why in one plain line, with the full `baton migrate` command when Baton runs from inside the folder. `baton migrate` exits 0 when it renamed the folder or had nothing to do, 3 when it kept the old name, and 1 on an error. When both names exist, Baton uses `~/Applications/Baton` and leaves the other alone.
- **Launchers are updated in place under the same lock.** Right after the rename, each launcher keeps its bundle folder, so Dock items still find it; its script, `Info.plist` and icon are written again with the engine's new path and the path `baton` has after the rename, then signed ad hoc and registered with Launch Services again. Launchers are never removed to be rebuilt, in the rename or in `baton refresh`.
- **Old names keep working where it costs nothing.** An old `Claude Profiles.app` that came along into `~/Applications/Baton` goes to the Trash; the install script saves every old copy it finds (in the install folder, the old launchers folder and `/Applications`) as a dated ZIP in `AppBackups` first, and prints the exact `ln -sf` for each `baton` or `claude-profiles` link in `/usr/local/bin` or `/opt/homebrew/bin` that points into the old app or folder. A Baton that starts while an old copy runs (`Claude Profiles.app`, a copy in the Trash, or an older version) quits that copy instead of handing over to it. The app bundle carries `Contents/Helpers/claude-profiles` as a relative link to `baton` for all of 1.x.
- **Claude's and Anthropic's settings from the environment stop at Baton.** The app and `baton` start by removing every environment variable whose name starts with `CLAUDE` or `ANTHROPIC_`, so a window opened from a terminal or a Claude Code session uses its own account's settings, not the caller's model, endpoint, key or config folder. Baton reads none of them itself.
- **The cask is renamed, not duplicated.** The tap gets `Casks/baton.rb` and `cask_renames.json` with `{"claude-profiles": "baton"}`, so `brew upgrade` moves existing users to the new token. The cask installs only `baton`, and its `zap` removes only `AppBackups`, caches and preferences, in the data folder under either name.

## Consequences

- An install from before 1.0 keeps its data in `~/Library/Application Support/Claude Profiles` for good. Only someone who reads that folder's name sees the old one, and nothing in Claude's data has to be rewritten.
- An upgrade with Claude windows still open keeps the launchers folder's old name until the next start with every Claude window closed, or until the printed `baton migrate`; nothing is lost in the meantime, and Baton works from the old folder.
- The bundle id and the launcher ids show the old name to anyone who reads `Info.plist`, `defaults` or the log. That is the price of keeping the Dock items, preferences and the one-copy check across the upgrade.
- A link someone made by hand into the old launchers folder, such as `/usr/local/bin/claude-profiles`, stops working once the old app or folder is gone and has to point at `~/Applications/Baton`; the install script prints the command for the usual places.
- Revisit if macOS gains a supported way to carry an app's records over to a new bundle id, or once 2.0 can drop the `claude-profiles` command.
